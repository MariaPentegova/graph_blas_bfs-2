# Сравнение BFS: Classic vs GraphBLAS

## О проекте

В проекте сравниваются два подхода к обходу графа в ширину (BFS):

* **Classic BFS** — последовательный BFS на C с очередью, граф хранится в формате CSR;
* **GraphBLAS BFS** — линейно-алгебраический BFS: граф хранится как разреженная матрица смежности, шаг обхода выражается через умножение вектора на матрицу (`SuiteSparse:GraphBLAS`).

Обе реализации есть в двух вариантах: из одной вершины (**single-source**) и одновременно из нескольких вершин (**multisource**). Обе возвращают одинаковый результат — **дерево предков** (`parent`), поэтому решают одну и ту же задачу и сравниваются на равных условиях.

**Цель проекта** — экспериментально сравнить производительность двух подходов на графах разной топологии (дорожные сети, социальные сети, веб-граф, граф цитирования; ориентированные и неориентированные) и определить, на каких графах выгоднее GraphBLAS, а на каких — классический BFS.

Дополнительно используется **Boost Graph Library (BGL)** — независимая библиотечная реализация BFS. Она нужна только для проверки правильности классической реализации и **не участвует** в основном сравнении с GraphBLAS. LAGraph в сравнение не включён: добавление других библиотек увеличило бы число факторов, влияющих на результат, и затруднило бы выделение влияния топологии графа.

---

## Что делает программа

1. Загружает граф из файла Matrix Market (`.mtx`), сохраняя направление рёбер.
2. Преобразует граф в CSR.
3. Выбирает стартовую вершину — вершину с максимальной исходящей степенью.
4. Выбирает четыре источника для multisource BFS (подробности — в «Методике»).
5. Один раз строит матрицу GraphBLAS и граф BGL; это время в замеры BFS не входит.
6. Измеряет время каждой реализации: 1 прогревочный прогон + 10 замеров.
7. Проверяет, что все реализации дали правильный и одинаковый результат.
8. Вычисляет характеристики обхода и печатает для каждого графа таблицу времени (Avg / Min / Max), ускорение, характеристики обхода и результаты проверок.

### Представление графа и результат

#### Matrix Market

Графы загружаются из `.mtx`. Поддерживаются квадратные матрицы без весов (pattern):
* **symmetric** — неориентированный граф: ребро добавляется в обе стороны (петля v - v — один раз);
* **general** — ориентированный граф: ребро u -> v добавляется только в одну сторону.

#### CSR (Compressed Sparse Row)

* `row_ptr` длины `n + 1`: соседи `v` лежат в `col_idx` с позиции `row_ptr[v]` до `row_ptr[v + 1] - 1`;
* `col_idx` — соседи всех вершин подряд.

Пример:
```text
row_ptr = [0, 2, 5, 6]
col_idx = [1, 3, 0, 2, 4, 1]
```
* Вершина 0 → соседи 1, 3
* Вершина 1 → соседи 0, 2, 4
* Вершина 2 → сосед 1

Для ориентированного графа в строке хранятся только исходящие рёбра. Соседи в каждой строке отсортированы, повторяющиеся рёбра удалены — обе реализации получают граф в одинаковом виде.

#### Формат результата

`parent`:
* источник: `parent[s] = s`;
* достижимая вершина: `parent[v]` — вершина, из которой `v` впервые достигнута;
* недостижимая: `parent[v] = -1`.

Классика (и BGL) пишут сразу в `int[]`. GraphBLAS возвращает разреженный вектор; для проверки он переводится в массив `graphblas_parent_to_array()` — это преобразование формата, в замер не входит.

Предок неоднозначен: вершину может открыть любой сосед предыдущего уровня. Деревья могут отличаться, но глубины (расстояния) и множество недостижимых вершин обязаны совпадать.

Все функции возвращают 0 при успехе и -1 при ошибке.

## Реализованные алгоритмы

### Classic BFS

```c
int csr_parent_bfs(const CSRMatrix* csr, int start_vertex, int* parent);
int csr_multisource_bfs(const CSRMatrix* csr, const int* sources, int num_sources, int* parent);
```

Очередь, вершины извлекаются по одной, просматриваются исходящие рёбра, непосещённые соседи получают предка и попадают в очередь. Multisource: все источники кладутся в очередь до начала (дубликаты — один раз). Время $O(V+E)$, память $O(V)$.

Обе функции вызывают внутреннюю `static run_bfs(...)`: single-source — частный случай multisource с одним источником. `run_bfs` — деталь реализации, тесты её не видят.

### GraphBLAS BFS

```c
int graphblas_parent_bfs(const CSRMatrix* csr, void* A_handle, int start_vertex, void** parent_out);
int graphblas_multisource_parent_bfs(const CSRMatrix* csr, void* A_handle, const int* sources, int num_sources, void** parent_out);
int graphblas_parent_to_array(void* parent_handle, int n, int* parent);
void graphblas_free_vector(void* vector_handle);
```

Граф — разреженная матрица `A`: `A(i,j)` есть, если есть ребро i->j. Два вектора:
* `parent` — предки посещённых (наличие элемента = вершина посещена);
* `frontier` — текущий фронт.

Пока фронт не пуст:
```text
frontier<!parent> = frontier * A     (полукольцо ANY.SECONDI)
parent<frontier>  = frontier
```

* `GrB_vxm` находит соседей фронта. Маска `!parent` оставляет непосещённых. `SECONDI` записывает в `j` номер `k` из фронта, откуда есть k->j, — это предок. При нескольких `k` `ANY` берёт любой.
* `GrB_Vector_assign` с маской `frontier` сохраняет новых предков.

Маска структурная (`GrB_DESC_RSC`): учитывается наличие элемента, а не значение, иначе вершина с предком 0 считалась бы непосещённой.

GraphBLAS неблокирующий, поэтому в конце — `GrB_Vector_wait(GrB_MATERIALIZE)`: он завершает отложенные операции, и весь обход попадает в измеряемое время. Без `wait` время было бы занижено.

Обе реализации делают один и тот же top-down обход по уровням. Direction-optimizing BFS не используется: это другой алгоритм, а сравниваются подходы при одной постановке.

Зависимость от SuiteSparse. Используются расширения `GxB_ANY_SECONDI_INT32`, `GxB_Matrix_import_CSR`, `GxB_Global_Option_get(GxB_NTHREADS)`. Проверено на версии 7.4.0; на произвольной реализации GraphBLAS код не соберётся без замены этих вызовов.

`graphblas_init()` / `graphblas_finalize()` вызываются по одному разу в `main`.

### Boost Graph Library BFS (контрольная реализация)

`boost::breadth_first_search` вызывается в `benchmark.cpp`. Граф `boost::compressed_sparse_row_graph` один раз до замеров строится из тех же рёбер CSR; предки пишутся `boost::record_predecessors` (`on_tree_edge`). Корень выставляется вручную: `record_predecessors` не пишет корень на `on_tree_edge`. Результат BGL сравнивается с классикой через `bfs_tree_depths`.

BGL однопоточный, как и классика, — сравнение по скорости идёт при равных ресурсах. В основном сравнении с GraphBLAS BGL не участвует: его роль — независимая проверка правильности классики.

### Проверка правильности результата

`bfs_tree_depths()` (в `utils.c`) по `parent` вычисляет глубину каждой вершины (-1 для непосещённых) и проверяет, что дерево — правильный результат BFS:
* в цепочках предков нет циклов и ссылок на непосещённые вершины;
* для каждой посещённой `v` (кроме корня) ребро `parent[v] -> v` есть в графе;
* для каждого ребра `u->v` из посещённой `u` вершина `v` тоже посещена и `depth[v] <= depth[u] + 1`.

Отсюда: глубина = кратчайшее расстояние, недостижимые помечены -1. Два результата BFS считаются одинаковыми, если оба дерева правильные и глубины совпадают. Проверка за $O(V+E)$. В бенчмарке вызывается после замеров, на время не влияет.

## Экспериментальное исследование

### Методика замеров

1. **Конфигурация:** Сборка в режиме `Release` с флагами `-O3 -DNDEBUG`.
2. **Потоки:** Классический BFS работает строго в один поток. Для GraphBLAS используется OpenMP на все доступные ядра — тестируем подходы в том виде, как их реально применяют на практике. Количество потоков выводится в лог (`GraphBLAS threads`), при желании его можно ограничить через `OMP_NUM_THREADS`.
3. **Итерации:** Для каждого графа делается 1 прогревочный прогон (чтобы исключить влияние холодных кэшей и ленивой аллокации памяти), а затем — 10 чистых замеров. В таблицах считаем среднее (`Avg`), минимум (`Min`) и максимум (`Max`) в микросекундах.
4. **Таймер:** Время замеряем с помощью `clock_gettime(CLOCK_MONOTONIC)`.
5. **Изоляция замеров:** Время на парсинг Matrix Market, построение CSR-структуры, матрицы GraphBLAS и графа BGL учитывается отдельно и в замеры самого BFS не входит.
6. **Границы замера:** Считаем только чистый обход и формирование результата. Для классики — это инициализация очереди, заполнение массива `parent` значениями `-1` и сам обход. Для GraphBLAS — создание векторов фронта, итерации обхода и обязательный вызов `GrB_Vector_wait` (так как библиотека неблокирующая, без этого замер будет некорректным). Конвертация вектора GraphBLAS обратно в массив для проверки в замер времени не включается.
7. **Точка старта (Single-source):** Выбираем вершину с максимальной исходящей степенью (`max out-degree`). Для ориентированных графов это не гарантирует стопроцентный охват, поэтому долю реально обойдённых вершин мы выводим отдельно.
8. **Источники для Multisource:** Генерируем 4 разные вершины с исходящей степенью > 0. Используем стандартный `std::mt19937` с фиксированным зерном `12345` (по аналогии с бенчмарком Graph500). Это делает тесты воспроизводимыми и исключает случайный выбор изолированных узлов.
9. **Валидация:** После каждого прогона результаты автоматически сверяются через `bfs_tree_depths()`. Проверяем классику с BGL (для самопроверки) и классику с GraphBLAS.

Ускорение GraphBLAS рассчитываем как отношение средних времён:
**S = T_Classic \ T_GraphBLAS**

Если S > 1, GraphBLAS быстрее классики; если S < 1 — классика.

### Метрики обхода (Traversal characteristics)

Эти параметры рассчитываются после всех замеров по эталонному дереву классической реализации. Они отражают сухую геометрию графа и не зависят от конкретного кода:

* **reached vertices** — сколько всего вершин удалось посетить (абсолютное число и процент от общего размера графа);
* **levels** — глубина обхода (количество уровней дерева + 1);
* **max level size** — пиковое количество вершин на одном (самом широком) уровне;
* **edges examined (\(M\))** — сумма исходящих степеней всех посещённых вершин. 
* **edges per level** — средний объём работы на один шаг обхода M \ levels;
* **MTEPS** (Million Traversed Edges Per Second) — стандартная метрика производительности BFS (как в Graph500). Считается как M \ T_Avg, где M — число просмотренных рёбер (в миллионах), а  T — среднее время обхода (в секундах). Позволяет адекватно сравнивать скорость работы на графах совершенно разного масштаба.

### 6. Контрольная проверка по Boost Graph Library (BGL)

Поскольку результаты независимой реализации BGL полностью совпали по глубинам с нашей классической версией на всех графах, корректность базового кода можно считать подтвержденной. При этом классический алгоритм показал время, сопоставимое или превосходящее BGL (в 1.06–2.33 раза быстрее), что исключает искусственное преимущество GraphBLAS из-за неоптимальной реализации базового конкурента. Результаты GraphBLAS также продемонстрировали стопроцентную сходимость с эталоном во всех тестах (single-source и multisource).

### Влияние топологии

Анализ характеристик обхода и результатов замеров показывает, что эффективность каждого подхода напрямую зависит от структуры исследуемого графа.

* **Объем работы на один уровень — ключевой фактор.** В исследуемой выборке графы четко разделились на две группы. На графах, где на один уровень обхода приходится менее \(130\) тысяч рёбер (дорожные сети, `cit-Patents`, `com-Amazon`, `web-Google`), классический алгоритм работает быстрее в обоих режимах (\(S = 0.12–0.91\)). Однако на социальных сетях (`com-Orkut` и `soc-LiveJournal1`), где этот показатель составляет от \(4.5\) до \(33\) миллионов рёбер, GraphBLAS демонстрирует явное преимущество, обеспечивая ускорение в \(3.03–4.67\) раза. Пересечений между группами не обнаружено.
* **Зависимость от структуры данных.** Производительность классического BFS относительно стабильна и колеблется в пределах \(24.9–136.3\) MTEPS. В то же время показатели GraphBLAS сильно скачут: от минимальных \(3.4\) MTEPS на патентах до максимальных \(417.2\) MTEPS на Оркуте. Это объясняется природой алгоритма: каждый шаг GraphBLAS — это линейно-алгебраическая операция над разреженными структурами. Накладные расходы на ее выполнение (включая распределение задач между 16 потоками) окупаются только при наличии широкого фронта работы. На графе `road_usa`, где обход идет последовательно по \(6809\) узким уровням (в среднем всего по \(8.5\) тыс. рёбер на уровень), накладные расходы нивелируют преимущества параллелизма.
* **Плотность связей (средняя степень).** Этот признак известен еще до запуска обхода. GraphBLAS выигрывает на графах с высокой средней степенью (\(14.2\) и \(76.3\)) и уступает классике на графах с малой степенью (\(2.4–5.6\)). Поскольку в выборке отсутствуют графы со средней степенью в диапазоне от \(5.6\) до \(14.2\), точную границу смены лидера определить пока невозможно.
* **Влияние ориентации рёбер и достижимости.** Сама по себе ориентация рёбер выбор не диктует (среди ориентированных графов GraphBLAS эффективен на `soc-LiveJournal1`, но уступает на `web-Google` и `cit-Patents`), однако она сильно влияет на размер зоны достижимости. В графе цитирования `cit-Patents` из-за специфики структуры (ссылки ведут только назад) обход охватывает лишь \(3.35\%\) вершин в single-source и \(1.20\%\) в multisource. В таких условиях GraphBLAS проигрывает сильнее всего (классический алгоритм быстрее в \(6.6–8.3\) раза): затраты библиотеки на обработку матрицы остаются высокими, тогда как у классического BFS просто быстро пустеет очередь.
* **Особенности графов web-Google и com-Amazon.** В режиме single-source на графе `web-Google` классика формально впереди (\(S = 0.91\)), однако временные диапазоны Min/Max пересекаются, что указывает на отсутствие значимой разницы. При этом в режиме multisource преимущество классики становится уверенным. Пример `com-Amazon` подтверждает, что тип графа вторичен: являясь по сути сетью связей покупателей, этот граф имеет малую среднюю степень (\(5.53\)) и узкие уровни, из-за чего ведет себя как дорожная сеть, где классический BFS стабильно быстрее.


**Вывод.** 
GraphBLAS эффективен на графах с высокой плотностью связей и небольшим числом уровней (социальные сети, ускорение до \(4.67\) раза). Классический BFS предпочтителен на разреженных графах с большой глубиной обхода (дорожные сети, быстрее до \(5–6.5\) раз), а также на ориентированных структурах, где из источника достижима лишь малая часть вершин (граф цитирования, быстрее до \(8.3\) раза).


### Ограничения

1. **Железо и потоки**. Мы сравнивали подходы, пользуясь многопоточностью графбласа, поэтому ресурсы получились неравными: классический алгоритм крутится в один поток, а GraphBLAS задействует сразу 16. Если захотите сравнить чисто голые алгоритмы на одном ядре — не забудьте выставить OMP_NUM_THREADS=1.
2. **Статистика**. На каждый граф делали всего по 10 замеров после одного прогревочного. Никаких доверительных интервалов и сложной математики тут нет, просто вывели среднее, минимум и максимум.
3. **Выбор стартовой точки**. В single-source мы всегда стартуем с вершины с максимальной исходящей степенью (max out-degree). Но на ориентированных графах вроде cit-Patents это не означает, что мы обойдем весь граф — там мы застряли на 3.35%. Так что провал GraphBLAS в этом тесте связан скорее с микроскопическим размером самого обхода, а не только с топологией.
4. **Белые пятна в выборке**. В наборе нет графов из «серой зоны» — со средней степенью между 5.6 и 14.2 и размером уровня от 130 тысяч до 4.5 млн рёбер. Поэтому нащупать точную границу, где именно GraphBLAS начинает обгонять классику, пока не получилось.
5. **Привязка к SuiteSparse**. В коде используются специфические расширения GxB_*. Собрать проект на какой-то другой реализации GraphBLAS не получится — придется переписывать эти вызовы.
6. Только Top-Down. Самый обычный BFS проходит по уровням. Оптимизации в духе Direction-optimizing (когда обход переключается на bottom-up на широких слоях) ни в одной из реализаций нет.
7. **Графы без весов**. Поддерживаются только pattern-матрицы. Если рёбрам нужны веса, текущий код не подойдёт.
8. **Лимит на размер графа**. Для индексов и row_ptr используется обычный int. Этого хватает с запасом для нашего самого большого графа com-Orkut (234 млн рёбер), но если захочется прогнать огромный граф на 2+ миллиарда рёбер, код упадёт — нужно будет переводить всё на int64.

### Тестирование

Все тесты лежат в `src/tests` и прогоняются через CTest. Внутри используется обычный `assert()`. Чтобы проверки не вырезались при Release-сборке (где CMake автоматом врубает `NDEBUG`), мы принудительно воткнули флаг `-UNDEBUG` для таргета `test_common`. Навесили на каждый тест таймаут в 60 секунд — если BFS где-то зациклится, CTest просто прибьёт процесс.

**test_common.c**
Для тестов вручную посчитали два небольших графа:
* Неориентированный на 5 вершин (0-1, 1-2, 0-3, 1-4, 3-4).
* Ориентированный на 4 вершины (0->1, 1->2, 3->0). На нём удобно проверять недостижимость: если стартовать из 0, 1 или 2, то в тройку мы никак не попадём.

**Что именно проверяем:**
* **test_load (Парсер):** Проверяем корректность сборки CSR-структуры. Смотрим, как код справляется с типами `symmetric` (должен дублировать рёбра в обе стороны) и `general` (пишет строго в одну сторону), как чистит дубликаты и сортирует соседей. Отдельно прогнали парсер на «битых» файлах: пустые матрицы, не-MatrixMarket формат, наличие весов, неквадратные сетки и индексы за границами.
* **test_check (Валидатор дерева):** Проверили, что функция `bfs_tree_depths` на самом деле ловит косяки в результате: циклы, левые рёбра, пропущенные вершины или не кратчайшие пути.
* **test_bfs (Работа алгоритмов):** Прогоняем обе реализации (Classic и GraphBLAS) во всех режимах. Проверяем single-source из каждой вершины и multisource (включая крайние случаи: дубли источников, частично или полностью невалидные ID вершин). Проверили поведение на изолированных вершинах и петлях. Для GraphBLAS отдельно убедились, что если все источники невалидны, функция возвращает пустой вектор, который потом корректно конвертируется в массив из `-1`.
* **test_comparison (Сквозное сравнение):** Финальный тест. Берём обе реализации, даём им одинаковые входные данные (все комбинации источников на тестовых графах) и проверяем, что на выходе получаются идентичные по глубинам деревья.

### Автоматическая проверка (GitHub Actions)

При push и PR (`.github/workflows/cmake.yml`) проект собирается и тестируется дважды:
1. `Release` — как для замеров;
2. `Debug` с AddressSanitizer и UndefinedBehaviorSanitizer — ловят выход за границы, use-after-free, утечки, UB, которые `assert()` не видит.

Новые проверки работают и в Release, и под санитайзерами: размеры `parent` соответствуют числу вершин тестовых графов, вся память освобождается.
