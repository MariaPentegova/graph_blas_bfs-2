# Сравнение BFS: классический подход и GraphBLAS

## О проекте

В работе сравниваются две парадигмы обхода графа в ширину:

- **Классический BFS** — императивный алгоритм на очереди поверх CSR-представления на языке C. Реализованы одноисточниковый (`parent`) и многоисточниковый варианты.
- **GraphBLAS BFS** — линейно-алгебраическая формулировка через матрично-векторное умножение над булевым полукольцом LOR-LAND средствами SuiteSparse:GraphBLAS. Также в одно- и многоисточниковом вариантах.

Дополнительно используется **Boost Graph Library (BGL)** — независимая библиотечная реализация BFS. Она выступает в роли контрольной версии для классической реализации и **не участвует** в основном сравнении с GraphBLAS. LAGraph в сравнение не включён: добавление других библиотек увеличило бы число факторов, влияющих на результат, и затруднило бы выделение влияния топологии графа.

**Цель** — экспериментальное исследование влияния топологических свойств графов (направленность ребер, плотность связей, диаметр) на производительность последовательного, линейно-алгебраического и эталонного шаблонного подходов, а также строгая сертификация качества разработанного CSR-решения на фоне мирового индустриального стандарта.

## Что реализовано

### Классический BFS

Императивный обход через очередь. Граф хранится в формате CSR (два массива `row_ptr`, `col_idx` на 32-битных `int`). Реализованы две функции:

- `csr_parent_bfs(csr, start, parent)` — строит дерево предков от одной вершины.
- `csr_multisource_bfs(csr, sources, k, parent)` — обход одновременно из `k` источников, все источники получают уровень 0.

Сложность O(V + E) по времени и O(V) по памяти на очередь. Используется компактная 32-битная адресация (`int` вместо `size_t`), что снижает объём кэш-промахов на графах до 2^31 вершин.

### GraphBLAS BFS

Матрица смежности `A` (булева, разреженная) строится один раз через `GxB_Matrix_import_CSR` — без копирования, прямо над массивами `row_ptr` и `col_idx`. Каждая итерация BFS:

```
new_frontier = frontier × A    (с маской visited)
```

Используется полукольцо **LOR-LAND**: умножение — логическое И, сложение — логическое ИЛИ. Уже посещённые вершины исключаются через инвертированную маску `visited` с дескриптором `GrB_OUTP=GrB_REPLACE, GrB_MASK=GrB_COMP`. Один уровень BFS = одна итерация `GrB_vxm`.

Реализованы `graphblas_level_bfs` и `graphblas_multisource_level_bfs`. Финальная выгрузка уровней — пакетный `GrB_Vector_extractTuples_INT32` (вместо поштучного `GrB_Vector_extractElement` в цикле — на графах с миллионами вершин это даёт заметную разницу).

### Boost BGL (контрольная версия)

`boost::compressed_sparse_row_graph` конструируется один раз над уже готовыми массивами `row_ptr` / `col_idx`. Запись предков — через стандартный визитор `boost::record_predecessors(parent, boost::on_tree_edge())`. Нужен не для «соревнования», а как эталон: если собственная C-реализация обгоняет или идёт наравне с BGL — значит, она как минимум не хуже зрелого промышленного образца.


## Представление графа

### Matrix Market

Графы загружаются из формата `.mtx` (SuiteSparse Matrix Collection). Поддерживаются квадратные `pattern`-матрицы в вариантах `symmetric` и `general`. Функция загрузки проверяет шапку, размерность, читает рёбра.

### CSR

Из списков смежности граф конвертируется в формат Compressed Sparse Row:

- `row_ptr` длины `n+1`: соседи вершины `v` лежат в `col_idx[row_ptr[v] .. row_ptr[v+1]-1]`.
- `col_idx`: все соседи подряд.

CSR даёт последовательное чтение памяти и позволяет строить GraphBLAS-матрицу и BGL-граф без копирования.


## Установка и сборка

### Требования

Проверено на:

- Ubuntu 26.04.1 LTS
- CMake 4.2.3
- g++ 15.2.0 (C11 и C++17)
- Boost 1.90 (`libboost-graph-dev` и заголовочные компоненты)
- **SuiteSparse:GraphBLAS 7.12.2** (пакет `libsuitesparse-dev` в Ubuntu 26.04)

**Важно про версию GraphBLAS.** Код использует `GxB_Matrix_import_CSR` с 13 аргументами (сигнатура v7). В v8/v9 сигнатура другая (12 аргументов, без `jumbled`), и файл `src/main/graphblas_bfs.c` не скомпилируется. Если собираете на другой версии — поправьте вызов импорта или установите v7.

### Установка зависимостей

```bash
sudo apt update
sudo apt install libsuitesparse-dev libboost-graph-dev cmake build-essential
```

### Получение графов через Git LFS

Графы весят от 12 МБ до 1.7 ГБ, суммарно около 3.5 ГБ, поэтому хранятся в Git LFS. Без LFS в `graphs/` окажутся не сами `.mtx`, а файлы-пустышки размером ~130 байт.

```bash
git lfs install
git clone https://github.com/<ваш-username>/graph_blas_bfs-2.git
cd graph_blas_bfs-2
git lfs pull
```

Если LFS не установлен — поставьте: `sudo apt install git-lfs && git lfs install`. Проверить, что графы скачались, можно по `ls -lh graphs/` (должны быть мегабайты/гигабайты, а не байты).

### Сборка

```bash
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
cmake --build . -j
```

`Release` обязателен: в `CMakeLists.txt` принудительно включается `-O3 -DNDEBUG`. Если собрать `Debug` — сравнение с предыдущими замерами будет некорректным.

Один граф, подробный вывод по каждому алгоритму:

```bash
./bfs_analysis ../graphs/com-Orkut.mtx
```

Бенчмарк по всем 7 графам (без аргументов) или по одному:

```bash

./bfs_benchmark ../graphs/soc-LiveJournal1.mtx
```


## Методика бенчмарка

- **10 прогонов** каждого алгоритма на каждом графе. Перед замерами каждый алгоритм запускается один раз без учёта в результат: первый запуск обычно медленнее следующих (процессор и память ещё не «проогрелись»), поэтому его результат в статистику не включается.
- Время измеряется через `clock_gettime(CLOCK_MONOTONIC)`.
- **Вне таймера**: загрузка `.mtx`, построение CSR, построение GraphBLAS-матрицы, построение BGL-графа. Это важно: иначе на `road_usa` (24M вершин) построение BGL-графа занимает ~360 мс и приписывается «медленности BGL», а не подготовке.
- **В таймере**: только сам вызов BFS-функции — от входа в неё до выхода. Всё, что происходит внутри (включая подготовку массивов вроде parent), входит в замер одинаково для всех реализаций.
- Приводятся Avg / Min / Max по 10 прогонам.
- Статистика по топологии (`max_level`, `avg_width`) считается **один раз** на граф: `max_level` — номер последнего уровня, до которого дошёл BFS, `avg_width` — среднее число вершин на непустой уровень.

Стартовая вершина для одноисточникового BFS — `find_max_degree_vertex` (вершина с максимальной исходящей степенью). Для многоисточникового — четыре вершины с индексами `0, n/4, n/2, 3n/4`.

## Анализ

На скорость BFS влияют три характеристики графа: **ширина фронта** (`avg_width`), **диаметр** (`max_level`) и **достижимость** из стартовой вершины, которая зависит в том числе от ориентированности. Ни одна из них не нивелирует действие других - важно их сочетание.

### Ориентированность задаёт верхнюю границу достижимости

В ориентированном графе из одной вершины часто достижимо лишь подмножество всех вершин: в `cit-Patents` — 3.3% (126 298 из 3 774 768), в `web-Google` — 65% (600 493 из 916 428), в `soc-LiveJournal1` — 91% (4 400 347 из 4 847 571). В неориентированных графах (`com-Amazon`, `com-Orkut`, `roadNet-CA`, `road_usa`) достижимы все вершины.

Это важно, потому что **широкий фронт возможен только там, где много достижимых вершин**. В `cit-Patents` из-за ориентированности и низкой достижимости BFS проходит всего 13 уровней по ~9 000 вершин — фронт узкий, и GraphBLAS не получает преимущества. В `com-Orkut` (неориентированный, достижимо 100%) фронт раздувается до 438 920 вершин на уровень — и GraphBLAS выигрывает.

Но одной ориентированности недостаточно: `soc-LiveJournal1` ориентированный, но достижимо 91%, и фронт широкий (314 310) — GraphBLAS выигрывает 3.65x. А `web-Google` ориентированный с достижимостью 65%, но фронт всего 20 016 — переходная хона. То есть ориентированность — это **фильтр, ограничивающий потенциал**, а не прямая причина.

### GraphBLAS выигрывает на широком фронте

`com-Orkut` (`avg_width=438 920`, `max_level=6`, неориентированный) и `soc-LiveJournal1` (`avg_width=314 310`, `max_level=13`, ориентированный, достижимо 91%) — графы с малым диаметром, где фронт BFS на первых же итерациях раздувается до сотен тысяч вершин. В этой ситуации `GrB_vxm` выполняется как плотная операция над разреженной матрицей, и накладные расходы окупаются. Итог: GraphBLAS в **3.65x** быстрее классики на обоих графах.

### Классика выигрывает на узком фронте при большом диаметре

`road_usa` (`avg_width=3 517`, `max_level=6808`, неориентированный) — дорожная сеть США. Фронт на каждом уровне — ~3 500 вершин, но уровней 6 808. GraphBLAS делает **6 808 вызовов `GrB_vxm`** (плюс `GrB_eWiseAdd`, `GrB_assign`, `GrB_Vector_nvals` на каждом шаге). Накладные расходы на вызов превышают время полезной работы, и GraphBLAS проигрывает в **22x**. Аналогично на `roadNet-CA` (`avg_width=2 692`, `max_level=726`, неориентированный) — проигрыш в 5.7x.

### Переходная зона

`web-Google` (`avg_width=20 016`, `max_level=29`, ориентированный, достижимо 65%) — единственный граф, где оба подхода дают сопоставимое время (0.81x — GraphBLAS чуть медленнее, но в пределах разброса). Это **не точная граница, а пример из переходной зоны**: при `avg_width` до ~12 000 (cit-Patents, com-Amazon, дорожные сети) уверенно выигрывает классика (0.04–0.49x), при `avg_width` от ~300 000 (soc-LiveJournal1, com-Orkut) — GraphBLAS (3.65x). Между этими значениями графов в выборке нет, поэтому точное положение перехода по имеющимся данным установить нельзя — это направление дальнейшей работы.

### Особый случай: cit-Patents

`cit-Patents` — ориентированный граф цитирования. Из max-degree вершины достижимо только 3.3% вершин. Сам BFS короткий (13 уровней, 126K вершин), но GraphBLAS всё равно в 8x медленнее — накладные расходы на итерацию `GrB_vxm` при крошечном фронте (~9 000 вершин на уровень) не окупаются. Это сочетание ориентированности (низкая достижимость) и узкого фронта. Кейс не опровергает общий вывод, а иллюстрирует его с другой стороны: мало работы — большие накладные расходы.

### BGL как контроль-версия

Boost BGL по времени везде **сопоставим с классикой** (0.47–1.24x в пользу то одного, то другого в зависимости от графа). Это подтверждает, что собственная C-реализация не уступает промышленному образцу, а на `road_usa` (1.64x быстрее BGL) и `cit-Patents` (2.11x быстрее) даже обгоняет.

## Тестирование

Автономная подсистема тестов в `src/tests/`, интегрирована с CTest.

```bash
ctest --output-on-failure
```

Три исполняемых файла:

- **`test_classic_bfs`** — проверяет дерево предков, построенное классическим BFS от одной вершины: корень указывает сам на себя, у остальных вершин предок не совпадает с самой вершиной, все вершины достижимы из стартовой. Отдельно проверяется от нескольких вершин: каждый источник указывает сам на себя, не-источники не указывают сами на себя.
- **`test_graphblas_bfs`** — проверяет уровни GraphBLAS. BFS от одного источника: все вершины достижимы, стартовая имеет уровень 0, у каждой вершины уровня k > 0 есть сосед уровня k−1 (инвариант BFS), уровни совпадают с эталоном для двух разных стартовых вершин. Multisource: все источники имеют уровень 0, уровни совпадают с эталоном, и для каждой вершины level_multi[i] <= level_single[i] (мультистарт не может дать большее расстояние, чем один источник).
- **`test_comparison`** — сквозное сравнение классики и GraphBLAS: для одного и того же графа и одинаковых источников уровни должны совпадать побитово. 

Тестовый граф — синтетический, 5 вершин, специально с циклами и тупиками. Генерируется в `test_utils.c`.


### Итог

Выбор между классическим BFS и GraphBLAS определяется **шириной фронта BFS** (`avg_width`), которая, в свою очередь, ограничена **диаметром графа** и **достижимостью из стартовой вершины**.

> **GraphBLAS выгоден на графах с широким фронтом BFS (`avg_width` в сотни тысяч) и малым диаметром (`max_level` ≤ 15).** Такие графы, как правило, неориентированные или слабо ориентированные с высокой достижимостью (соцсети `com-Orkut`, `soc-LiveJournal1`).
>
> **Классический BFS выгоден на графах с узким фронтом (`avg_width` тысячи) и большим диаметром (`max_level` сотни и тысячи).** Сюда попадают дорожные сети (`road_usa`, `roadNet-CA`), а также ориентированные графы с низкой достижимостью из одной вершины (`cit-Patents`).
>
> **Ориентированность** сама по себе не определяет выбор, но задаёт верхнюю границу достижимости: в ориентированных графах фронт BFS часто не может стать широким, что смещает выбор в сторону классики.

Точные границы перехода по имеющимся 7 графам не установлены — в выборке нет графов с `avg_width` в диапазоне 20 000–300 000. Это направление дальнейшей работы.
