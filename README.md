# Сравнение BFS: Classic vs GraphBLAS

## О проекте

В проекте сравниваются два подхода к обходу графа в ширину (BFS):

* **Classic BFS** — последовательный BFS на C с очередью, граф хранится в формате CSR;
* **GraphBLAS BFS** — линейно-алгебраический BFS: граф хранится как разреженная матрица смежности, шаг обхода выражается через умножение вектора на матрицу (`SuiteSparse:GraphBLAS`).

Обе реализации есть в двух вариантах: из одной вершины (**single-source**) и одновременно из нескольких вершин (**multisource**). Обе возвращают одинаковый результат — **дерево предков** (`parent`), поэтому решают одну и ту же задачу и сравниваются на равных условиях.

**Цель проекта** — экспериментально сравнить производительность двух подходов на графах разной топологии (дорожные сети, social-сети, веб-граф, граф цитирования; ориентированные и неориентированные) и определить, на каких графах выгоднее GraphBLAS, а на каких — классический BFS.

Дополнительно используется **Boost Graph Library (BGL)** — независимая библиотечная реализация BFS. Она нужна только для проверки того, что классическая реализация работает правильно, и **не участвует** в основном сравнении с GraphBLAS. LAGraph в сравнение не включён: добавление других библиотек увеличило бы число факторов, влияющих на результат, и затруднило бы выделение влияния топологии графа.

---

## Что делает программа

1. Загружает граф из файла формата Matrix Market (`.mtx`), сохраняя направление рёбер.
2. Преобразует граф в формат CSR.
3. Выбирает стартовую вершину — вершину с максимальной исходящей степенью.
4. Выбирает четыре источника для multisource BFS: случайные различные вершины с ненулевой исходящей степенью (фиксированное начальное значение генератора, поэтому выбор воспроизводим).
5. Один раз строит матрицу GraphBLAS и граф BGL (это время в замеры BFS не входит).
6. Измеряет время работы каждой реализации.
7. Проверяет, что все реализации дали правильный и одинаковый результат.
8. Вычисляет характеристики обхода (доля достигнутых вершин, число уровней, рёбер на уровень, MTEPS).

### Представление графа

#### Matrix Market
Графы загружаются из файлов формата Matrix Market (`.mtx`). Поддерживаются квадратные матрицы без весов (pattern):
* **symmetric** — неориентированный граф: ребро добавляется в обе стороны (петля `v - v` — один раз);
* **general** — ориентированный граф: ребро `u -> v` добавляется только в одну сторону.

#### CSR (Compressed Sparse Row)
После загрузки граф хранится в формате CSR в двух массивах:
* **row_ptr** — массив длины `n + 1`: соседи вершины `v` лежат в `col_idx` с позиции `row_ptr[v]` до `row_ptr[v + 1] - 1`;
* **col_idx** — соседи всех вершин подряд.

Пример:
```text
row_ptr = [0, 2, 5, 6]
col_idx = [1, 3, 0, 2, 4, 1]
```
* Вершина 0 → соседи 1, 3
* Вершина 1 → соседи 0, 2, 4
* Вершина 2 → сосед 1

Для ориентированного графа в строке вершины хранятся только её исходящие рёбра.

Рёбра из файла сначала читаются в два массива (начала и концы рёбер), затем по степеням вершин сразу раскладываются в CSR — без выделения памяти под каждое ребро отдельно. Соседи в каждой строке сортируются по возрастанию, повторяющиеся рёбра удаляются. Поэтому классическая реализация и GraphBLAS получают граф в одинаковом виде.

#### Формат результата
Результат BFS — дерево предков `parent`:
* для источника: `parent[s] = s`;
* для остальных достижимых вершин: `parent[v]` — вершина, из которой `v` была впервые достигнута;
* для недостижимых вершин: `parent[v] = -1`.

Классический BFS (и BGL) записывает результат сразу в массив `int` длины `n`. GraphBLAS возвращает результат в своём формате — разреженном векторе, где у недостижимых вершин просто нет элемента. Для проверки вектор переводится в такой же массив функцией `graphblas_parent_to_array()`; это преобразование формата, а не часть обхода, поэтому в замер времени оно не входит.

В BFS предок вершины определён неоднозначно: вершину может открыть любой её сосед с предыдущего уровня. Поэтому деревья разных реализаций могут отличаться, но глубины вершин в дереве (расстояния от источника) и множество недостижимых вершин обязаны совпадать.

Все функции BFS возвращают `0` при успехе и `-1` при ошибке (неверная стартовая вершина, `NULL`-указатель, нехватка памяти).

## Реализованные алгоритмы

### Classic BFS

```c
int csr_parent_bfs(const CSRMatrix* csr, int start_vertex, int* parent);
int csr_multisource_bfs(const CSRMatrix* csr, const int* sources, int num_sources, int* parent);
```

Классический BFS с очередью. Вершины извлекаются из очереди по одной, просматриваются их исходящие рёбра, ещё не посещённые соседи получают предка и добавляются в очередь. В multisource-варианте перед началом обхода в очередь кладутся все источники (повторяющиеся источники добавляются один раз). Время работы — $O(V+E)$, дополнительная память — $O(V)$ на очередь.

Обе публичные функции вызывают внутреннюю `static run_bfs(...)`: single-source — это частный случай multisource с одним источником, поэтому дублировать цикл обхода не нужно. `run_bfs` объявлена `static`, то есть является деталью реализации; тесты её не видят и работают только через публичный интерфейс.

### GraphBLAS BFS

```c
int graphblas_parent_bfs(const CSRMatrix* csr, void* A_handle, int start_vertex, void** parent_out);
int graphblas_multisource_parent_bfs(const CSRMatrix* csr, void* A_handle, const int* sources, int num_sources, void** parent_out);
int graphblas_parent_to_array(void* parent_handle, int n, int* parent);
void graphblas_free_vector(void* vector_handle);
```

Граф хранится как разреженная матрица смежности `A`: элемент `A(i, j)` есть, если есть ребро `i -> j`. Используются два разреженных вектора:
* **parent** — предки уже посещённых вершин (какие элементы есть в векторе = какие вершины посещены);
* **frontier** — текущий фронт BFS.

Пока фронт не пуст, повторяются два шага:
```text
frontier<!parent> = frontier * A     (полукольцо ANY.SECONDI)
parent<frontier>  = frontier
```

1. Умножение вектора фронта на матрицу (`GrB_vxm`) находит соседей вершин фронта. Маска `!parent` оставляет только ещё не посещённые вершины. Операция `SECONDI` записывает в найденную вершину `j` номер `k` вершины фронта, из которой есть ребро `k -> j`, — это и есть предок. Если таких `k` несколько, `ANY` берёт любой из них.
2. Новые предки сохраняются в векторе `parent` (`GrB_Vector_assign` с маской `frontier`).

Маска структурная (`дескриптор GrB_DESC_RSC`): учитывается только наличие элемента, а не его значение, иначе вершина с предком 0 считалась бы непосещённой.

GraphBLAS работает в неблокирующем режиме и может откладывать часть вычислений. Поэтому в конце обхода вызывается `GrB_Vector_wait`: он завершает все отложенные операции, и весь обход гарантированно попадает в измеряемое время. Без этого вызова время GraphBLAS было бы занижено.

Обе реализации выполняют один и тот же алгоритм — обход «сверху вниз» по уровням (top-down): на каждом уровне просматриваются исходящие рёбра вершин фронта. Различается только способ представления графа и обработки фронта: очередь и списки CSR у классики, операции над разреженной матрицей и векторами у GraphBLAS. Комбинированный обход с переключением направления (direction-optimizing BFS) не используется ни в одной реализации, так как это уже другой алгоритм, а сравниваются подходы при одной и той же постановке задачи.

**Зависимость от SuiteSparse.** Код использует расширения `SuiteSparse:GraphBLAS` — `GxB_ANY_SECONDI_INT32`, `GxB_Matrix_import_CSR`, `GxB_Global_Option_get(GxB_NTHREADS)`. Проверено на версии 7.4.0; на произвольной реализации GraphBLAS код не соберётся без замены этих вызовов на стандартные аналоги.

В модуле нет глобальных переменных: используются только встроенные объекты GraphBLAS. Функции `graphblas_init()` и `graphblas_finalize()` вызываются по одному разу в начале и в конце программы.

### Boost Graph Library BFS (контрольная реализация)

Используется готовая функция `boost::breadth_first_search` из BGL, она вызывается в `benchmark.cpp`. Граф BGL (`boost::compressed_sparse_row_graph`) один раз до замеров строится из тех же рёбер CSR, предки записываются стандартным визитором `boost::record_predecessors` (событие `on_tree_edge`). Корень выставляется вручную: `record_predecessors` не записывает корень на `on_tree_edge`. Результат BGL сравнивается с результатом классического BFS через `bfs_tree_depths`.

BGL однопоточный, как и классический BFS, поэтому сравнение по скорости с классикой идёт при равных ресурсах. В основном сравнении с GraphBLAS BGL не участвует: его роль — независимая проверка правильности классической реализации и контроль того, что классика не уступает по скорости готовой библиотечной реализации.

## Проверка правильности результата

Функция `bfs_tree_depths()` (модуль `utils`) используется и в тестах, и в бенчмарке. По массиву `parent` она вычисляет глубину каждой вершины в дереве (число рёбер до корня, `-1` для непосещённых) и проверяет, что дерево — правильный результат BFS:
* в цепочках предков нет циклов и ссылок на непосещённые вершины;
* для каждой посещённой вершины `v` (кроме корня) ребро `parent[v] -> v` есть в графе;
* для каждого ребра `u -> v` из посещённой вершины `u` вершина `v` тоже посещена и `depth[v] <= depth[u] + 1`.

Из этих условий следует, что глубина каждой вершины равна кратчайшему расстоянию от источников, а недостижимые вершины помечены `-1`. Поэтому два результата BFS считаются одинаковыми, если оба дерева правильные и глубины всех вершин совпадают. Проверка выполняется за $O(V+E)$.

В бенчмарке `bfs_tree_depths` вызывается после всех замеров, поэтому на время не влияет.

## Сборка

### Требования
* CMake 3.10 или новее;
* компилятор с поддержкой C11 и C++17 (`gcc/g++` или `clang/clang++`);
* SuiteSparse:GraphBLAS (сборка, тесты и замеры выполнены на версии 7.4.0; используются расширения `GxB_*`);
* Boost (заголовочные файлы Boost Graph Library).

### Получение графов (Git LFS)

Графы исследования лежат в каталоге `graphs/` и хранятся через Git LFS (Git Large File Storage): сами большие файлы находятся на сервере LFS, а в репозитории хранятся только ссылки на них. Без Git LFS вместо графов скачаются небольшие текстовые файлы-ссылки.

1. Установите Git LFS:
   ```bash
   sudo apt install git-lfs
   git lfs install
   ```
2. Склонируйте репозиторий — графы скачаются вместе с ним:
   ```bash
   git clone <адрес репозитория>
   ```
3. Если репозиторий уже был склонирован без Git LFS, скачайте графы отдельно (из каталога репозитория):
   ```bash
   git lfs pull
   ```
4. Чтобы скачать только один граф:
   ```bash
   git lfs pull --include="graphs/com-Amazon.mtx"
   ```

Проверить, что графы скачались: `git lfs ls-files` показывает список файлов, хранящихся в LFS, а `ls -lh graphs` — их размеры. Если файл весит около 130 байт и начинается со строки `version https://git-lfs.github.com/spec/v1`, это ссылка, а не граф: выполните `git lfs pull`. При запуске на такой ссылке программа сообщит `Error: not a Matrix Market file`.

Графы можно скачать и напрямую из SuiteSparse Matrix Collection (<https://sparse.tamu.edu>) в формате Matrix Market: `SNAP/cit-Patents`, `SNAP/com-Amazon`, `SNAP/com-Orkut`, `SNAP/roadNet-CA`, `DIMACS10/road_usa`, `SNAP/soc-LiveJournal1`, `SNAP/web-Google`. Файл `.mtx` из архива кладётся в каталог `graphs/` под именем графа (например, `graphs/web-Google.mtx`).

## Экспериментальное исследование

### Методика
1. Сборка Release (`-O3 -DNDEBUG`).
2. Классический BFS — последовательный (один поток). GraphBLAS работает параллельно на всех доступных ядрах процессора (OpenMP): возможность выполнять операции над разреженными матрицами и векторами параллельно — одно из основных свойств линейно-алгебраического подхода, и в работе сравниваются именно подходы в том виде, в котором они применяются на практике. Число потоков GraphBLAS программа печатает для каждого графа (строка `GraphBLAS threads`); при необходимости его можно ограничить переменной окружения `OMP_NUM_THREADS`.
3. Для каждого графа каждая реализация запускается 1 раз для прогрева и затем 10 раз с измерением времени. Вычисляются среднее (Avg), минимальное (Min) и максимальное (Max) время в микросекундах.
4. Время измеряется функцией POSIX `clock_gettime()` с часами `CLOCK_MONOTONIC`.
5. Построение CSR, матрицы GraphBLAS и графа BGL выполняется один раз до замеров и во время BFS не входит.
6. В замер входит только сам обход и подготовка его результата в родном формате реализации: для классики — заполнение массива `parent` (включая начальную запись -1 и queue), для GraphBLAS — создание векторов, обход и завершение отложенных операций (`GrB_Vector_wait`). Перевод вектора GraphBLAS в массив и проверка результата выполняются вне замера.
7. Стартовая вершина single-source BFS — вершина с максимальной исходящей степенью, чтобы обход не заканчивался сразу. Для ориентированного графа это не гарантирует, что из неё достижима большая часть графа, поэтому доля достигнутых вершин печатается.
8. Источники multisource BFS — четыре различные вершины с ненулевой исходящей степенью, выбранные равномерно случайно генератором `std::mt19937` с фиксированным начальным значением 12345 (как выбираются корни в Graph500). Такой выбор не подстраивается под структуру графа, исключает изолированные источники и одинаков при каждом запуске.
9. После замеров результаты всех реализаций сверяются с помощью `bfs_tree_depths()`: Classic с BGL, Classic с GraphBLAS.

Ускорение GraphBLAS относительно классической реализации:
$$S = rac{T_{Classic}}{T_{GraphBLAS}}$$

$S > 1$ означает, что быстрее GraphBLAS, $S < 1$ — что быстрее классический BFS.

### Характеристики обхода
Чтобы связывать время работы с топологией графа по измеренным величинам, а не по предположениям, программа для каждого обхода печатает блок `Traversal characteristics`. Он вычисляется по проверенному дереву классической реализации после всех замеров и на время не влияет. Характеристики не зависят от реализации:
* **reached vertices** — число и доля достигнутых вершин;
* **levels** — число уровней обхода (максимальная глубина + 1);
* **max level size** — число вершин на самом большом уровне;
* **edges examined** — число просмотренных рёбер $M$: сумма исходящих степеней достигнутых вершин (именно эти рёбра просматривает обход по уровням в обеих реализациях);
* **edges per level** — $M / levels$, объём работы на одном шаге обхода;
* **MTEPS** — миллионы просмотренных рёбер в секунду, $M / T$ (стандартная мера скорости BFS, позволяет сравнивать графы разного размера).

Кроме того, для каждого графа печатается средняя исходящая степень (Average out-degree) — характеристика, известная до обхода.

### Влияние топологии

1. **Выбор подхода определяется объёмом работы на одном уровне обхода.** На всех графах, где на уровень приходится не более $1.3 \cdot 10^5$ рёбер (дорожные сети, cit-Patents, com-Amazon, web-Google), классический BFS быстрее в обоих режимах ($S = 0.12–0.91$). На обеих социальных сетях, где на уровень приходится от $4.5 \cdot 10^6$ до $3.3 \cdot 10^7$ рёбер, быстрее GraphBLAS ($S = 3.03–4.67$). Пересечений между группами нет.
2. **Скорость GraphBLAS сильно зависит от графа, скорость классики — слабо.** Классический BFS обрабатывает 24.9–136.3 MTEPS, GraphBLAS — от 3.4 до 417.2 MTEPS. Каждый уровень GraphBLAS выполняется одной операцией над разреженными структурами, и её накладные расходы (в том числе на распределение работы между 16 потоками) окупаются только при большом числе рёбер на уровне. На com-Orkut (7 уровней по $3.3 \cdot 10^7$ рёбер) GraphBLAS обрабатывает 413 MTEPS против 136 у классики, на road_usa (6 809 уровней по $8.5 \cdot 10^3$ рёбер) — 11.7 MTEPS против 59.6.
3. **Средняя степень — признак, известный до обхода.** GraphBLAS выигрывает только на двух грахах со средней степенью 14.2 и 76.3, на всех пяти грахах со средней степенью 2.4–5.6 проигрывает. Графов со средней степенью 5.6–14.2 и с $1.3 \cdot 10^5 – 4.5 \cdot 10^6$ рёбер на уровень в наборе нет, поэтому точная граница между подходами не установлена.
4. **Ориентация рёбер сама по себе выбор не определяет** (среди ориентированных графов GraphBLAS выигрывает на soc-LiveJournal1 и проигрывает на web-Google и cit-Patents), но влияет через множество достижимых вершин. В cit-Patents ссылки ведут только на ранее выданные патенты, и даже из вершины с максимальной степенью достижимо 3.35% вершин (из четырёх случайных источников — 1.20%). Здесь GraphBLAS проигрывает сильнее всего ($S = 0.12$ и $0.15$, 3.4 MTEPS): 4.4 мс на уровень против 0.36–0.72 мс на дорожных сетях с уровнями того же порядка, хотя в road_usa вершин в 6 раз больше. Когда из источника достижима малая часть большого графа, затраты GraphBLAS не уменьшаются пропорционально объёму обхода.
5. **web-Google, single-source:** $S = 0.91$, но диапазоны времени пересекаются (52.6–89.9 и 76.1–95.3 мс) — значимой разницы нет. При multisource классика быстрее и здесь: её максимум меньше минимума GraphBLAS.
6. **Multisource не изменил вывода ни для одного графа:** каждый граф остался в той же группе.
7. **com-Amazon** — социальный по типу, но со средней степенью 5.53 и 64 тысячами рёбер на уровень; классика быстрее ($S = 0.71$ и $0.53$). Решает не тип графа, а объём работы на уровень.

**Итог:** GraphBLAS выгоден на графах с большой средней степенью и малым числом уровней обхода (социальные сети, ускорение 3.03–4.67 раза). Классический BFS выгоден на графах с малой степенью вершин и узкими уровнями (дорожные сети — быстрее в 3.6–6.5 раза) и на ориентированных грахах, где из источника достижима малая часть вершин (cit-Patents — быстрее в 6.5–8.4 раза).

### Ограничения
При интерпретации результатов нужно учитывать следующее:
1. **Разные ресурсы процессора.** Классика — один поток, GraphBLAS — 16 потоков. Это сравнение подходов в том виде, как их применяют на практике, а не алгоритмов при равных ресурсах. Чтобы сравнить при равных ресурсах, задайте `OMP_NUM_THREADS=1` — тогда $S$ покажет эффект только линейно-алгебраического представления.
2. **Один запуск на граф и 10 замеров.** Доверительных интервалов и статистических критериев нет; Avg/Min/Max приведены для прозрачности. Для web-Google single-source диапазоны пересекаются, и вывод там — «значимой разницы нет», а не «классика быстрее».
3. **Стартовая вершина — с максимальной исходящей степенью.** Для ориентированных графов это не гарантирует большую достижимость: в cit-Patents из неё достижимо 3.35% вершин. Вывод «классика быстрее на cit-Patents» частично объясняется малой достижимостью, а не только топологией.
4. **Нет графов в промежуточной области** (средняя степень 5.6–14.2, $1.3 \cdot 10^5 – 4.5 \cdot 10^6$ рёбер на уровень). Точная граница между подходами не установлена.
5. **Зависимость от SuiteSparse.** Используются `GxB_ANY_SECONDI_INT32`, `GxB_Matrix_import_CSR`, `GxB_Global_Option_get`. На другой реализации GraphBLAS код не соберётся без замены этих вызовов.
6. **Только top-down BFS.** Direction-optimizing (bottom-up на широких уровнях) не используется ни в одной реализации. С ним GraphBLAS мог бы выигрывать и на некоторых грахах с узкими уровнями, но это уже другой алгоритм.
7. **Только pattern-матрицы без весов.** Взвешенные графы и матрицы с явными значениями не поддерживаются.
8. **int для индексов и row_ptr.** Для графов с более чем 2.1 млрд рёбер нужен `int64`; в наборе максимальный com-Orkut — 234 млн рёбер, запас есть, но для будущих графов он невелик.

## Тестирование

Тесты находятся в каталоге `src/tests` и запускаются через CTest. Проверки записаны через `assert()`. Внутри `assert()` нет вызовов с побочными эффектами: сначала вызывается функция и сохраняется результат, затем проверяется условие. Чтобы `assert()` работал и в сборке Release (где CMake определяет `NDEBUG`), для тестовых целей в `CMakeLists.txt` добавлена опция `-UNDEBUG` (на цели `test_common` с `PUBLIC`, поэтому она действует на все четыре теста).

Тесты разделены на четыре программы, каждая запускается через CTest отдельно. Общие тестовые графы находятся в `test_common.c`:
* неориентированный граф из 5 вершин (рёбра 0-1, 1-2, 0-3, 1-4, 3-4);
* ориентированный граф из 4 вершин (рёбра 0->1, 1->2, 3->0): из вершин 0, 1, 2 вершина 3 недостижима, так как ребро 3->0 нельзя пройти в обратную сторону.

Ожидаемые расстояния для каждой стартовой вершины посчитаны вручную.

Новые проверки добавлены внутрь существующих файлов тестов, новых целей сборки нет: `CMakeLists.txt` не менялся, все четыре теста уже регистрировались в CTest через `foreach(test_name test_load test_check test_bfs test_comparison)`.

* **test_load** — загрузка графа. Тест записывает небольшие файлы `.mtx` и проверяет:
  * неориентированный граф (`symmetric`): рёбра добавляются в обе стороны, петля — один раз, массивы CSR совпадают с ожидаемыми, пропускаются строки-комментарии, учитывается нумерация вершин с 1;
  * ориентированный граф (`general`): обратные рёбра не добавляются;
  * соседи в строках CSR отсортированы, повторяющиеся рёбра удалены;
  * некорректные файлы отклоняются: не Matrix Market, матрица с весами, неквадратная матрица, номер вершины вне диапазона, рёбер меньше, чем объявлено, файл не существует;
  * пустой граф (0 вершин) отклоняется;
  * граф из одной вершины с петлёй: петля хранится один раз;
  * поиск вершины с максимальной исходящей степенью.
* **test_check** — функция проверки `bfs_tree_depths()` действительно находит ошибки: несуществующее ребро, цикл, пропущенная вершина, не кратчайший путь. Отдельно проверяется, что функция принимает корректное дерево с изолированной вершиной и отвергает неверного предка у неё.
* **test_bfs** — обе реализации (`Classic` и `GraphBLAS`), каждый случай прогоняется через обе:
  * BFS из каждой вершины обоих графов: результат — правильное дерево BFS, глубины равны ожидаемым расстояниям;
  * multisource BFS на обоих грахах, в том числе с повторяющимися источниками, с источниками вне диапазона (они игнорируются) и без единого правильного источника (все вершины недостижимы);
  * на ориентированном грахе массив `parent` совпадает с ожидаемым целиком (направление рёбер учитывается, недостижимая вершина получает -1);
  * граф с изолированной вершиной и петлёй: петля не меняет глубину, изолированная вершина остаётся -1; проверяются обе реализации;
  * неверные аргументы отклоняются (функции возвращают -1), при ошибке GraphBLAS BFS не возвращает вектор (`NULL`);
  * для GraphBLAS отдельно проверяется случай, когда все источники невалидны: функция возвращает успех, `*parent_out` — не `NULL`, а пустой вектор, после перевода в массив все вершины -1.
* **test_comparison** — прямое сравнение Classic и GraphBLAS:
  * для каждой пары источников на обоих общих грахах: оба результата — правильные деревья, глубины совпадают;
  * то же самое на грахе с изолированной вершиной.

Каждому тесту задан тайм-аут 60 секунд: если BFS зависнет, тест будет считаться проваленным.

### Автоматическая проверка (GitHub Actions)
При каждом push и pull request (`.github/workflows/cmake.yml`) проект собирается и тестируется дважды:
* в режиме **Release** — так же, как для замеров;
* в режиме **Debug** с санитайзерами *AddressSanitizer* и *UndefinedBehaviorSanitizer*. Они находят ошибки, которые `assert()` обнаружить не может: выход за границы массива, обращение к освобождённой памяти, утечки памяти, неопределённое поведение.

Добавленные проверки работают и в Release, и под санитайзерами: размеры массивов `parent` в них соответствуют числу вершин тестовых графов, а вся выделенная память освобождается (`graphblas_free_vector`, `graphblas_free_matrix`, `delete_csr`).

### Запуск тестов

В каталоге `build`:
```bash
ctest --output-on-failure
```
или каждый тест отдельно:
```bash
./test_load
./test_check
./test_bfs
./test_comparison
```

Ожидаемый вывод `test_bfs`:
```text
GraphBLAS initialized
PASSED: single-source BFS from every vertex
PASSED: multisource BFS
PASSED: edge directions are respected
PASSED: invalid arguments are rejected
PASSED: isolated vertex and loop
PASSED: all-invalid sources give an empty result vector
All BFS tests passed
```
